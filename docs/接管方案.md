# 接管方案：dsh-pet-android 当「身体」，我们的 AI 层当「脑子」

> 本文回答任务书的 8 个问题。所有结论都带 `文件:行号` 依据，行号对应当前工作区快照（`refs/` 为上游冻结副本，全程只读）。
> 表述口径：本仓库能证明的，给行号；本仓库证明不了的（例如真机温控与厂商冻结策略），一律进文末「待测清单」，不在此处给结论。

## 0. 结论先行

1. **接手方式是「换壳保脑」**：dsh-pet-android 替换 Coopanion 的 WebView 渲染链，作为桌面层的唯一实现；我们的 AI 层（语音 / LLM / Mattermost / 本地记忆）作为一个进程内控制器挂在 `PetService` 上，不新开服务、不新开 WebView。
2. **AI 层只有一条插入路径**（第 4 节）：新增 `ai/` 包 8 个文件，改 3 个既有文件共 9 处，`Pet.kt` / `Physics.kt` / `Lines.kt` / `tools/**` 一行不动。
3. **气泡是唯一的显示出口**：`PetService.say(pet, text)`（`PetService.kt:371`）是全仓库唯一把字符串画到屏幕上的地方，AI 文本必须走它，不要另建渲染。
4. **资源账能闭合**：480p 素材盘 274.5MB + 非素材 2.5MB = 277MB，与 Release 标注一致（`README.md:28`）；荣耀 80GT（16GB，可用 8–9GB）在 1–2 只宠物下峰值 238MiB，占可用内存 2.6%，装得下（第 7 节）。
5. **迁移是「三件套搬家 + 一大坨丢弃」**：`Brain.kt` / `Mattermost.kt` / `PetVoice.kt` / `LocalTalk.kt` / `PetSafety.kt` / `PetScript.kt` 六个文件可直接搬；WebView 渲染链、736 行本地 HTTP 服务器、无障碍与通知监听整套丢弃（第 8 节）。

## 1. 悬浮窗是怎么实现的

**API 组合**：`WindowManager.addView` + 手写 `WindowManager.LayoutParams`，每只宠物一个独立窗口，窗口层级统一用 `TYPE_APPLICATION_OVERLAY`。全仓库只有三处窗口，类型完全相同：宠物窗口 `PetService.kt:294`、气泡窗口 `PetService.kt:416`、长按动作菜单 `PetService.kt:712`。没有 `TYPE_PHONE` / `TYPE_SYSTEM_ALERT` 分支，因为 `minSdk 28`（`app/build.gradle.kts:12`）已经保证 `TYPE_APPLICATION_OVERLAY` 可用，被接管方不需要再维护旧机型分支。

**LayoutParams 逐项**（`PetService.kt:291-303`）：

| 项 | 取值 | 行号 | 作用 |
|---|---|---|---|
| width / height | `pet.sizePx` / `pet.heightPx` | `PetService.kt:292-293` | 窗口就是宠物的包围盒，随动画尺寸变（`Pet.kt:624-632` 同步回 LP） |
| type | `TYPE_APPLICATION_OVERLAY` | `PetService.kt:294` | 浮在所有应用之上、系统关键层（状态栏、输入法）之下 |
| flags | `FLAG_NOT_FOCUSABLE` | `PetService.kt:295` | 不抢焦点，桌宠不吃键盘事件 |
| flags | `FLAG_NOT_TOUCH_MODAL` | `PetService.kt:296` | 窗口外的手势透传给下层应用，这是「不挡事」的关键 |
| flags | `FLAG_LAYOUT_NO_LIMITS` | `PetService.kt:297` | 允许贴边躲藏时把身体挪出屏幕边缘（`Pet.kt:99-101` 的 hide 位移） |
| flags | `FLAG_HARDWARE_ACCELERATED` | `PetService.kt:298` | WebP 动画解码后走硬件合成 |
| format | `PixelFormat.TRANSLUCENT` | `PetService.kt:299` | 半透明像素格式，配合 webp 的 alpha 通道 |
| gravity | `TOP or START` | `PetService.kt:301` | 坐标以左上角为原点，物理引擎按屏幕坐标算 |
| x / y | `pet.x` / `pet.y` | `PetService.kt:302-303` | 初始位置来自配置的 corner/margin（`PetConfig.kt:65-80`） |

**层级**：`TYPE_APPLICATION_OVERLAY` 的层级由系统固定（介于 `TYPE_APPLICATION` 与 `TYPE_SYSTEM_*` 之间），本仓库不设 `lp.type` 之外的层控手段；三只宠物之间没有 z-order 配置项，顺序等于 `addView` 顺序（`PetService.kt:309`）。气泡窗口用 `FLAG_NOT_TOUCHABLE`（`PetService.kt:418`）保证点气泡等于点下层，绝不拦手势。

**触摸区域**：就是整个包围盒矩形，没有做不规则形状裁剪。README 把这条写成已知限制（`README.md:135`）。触摸全部交给自绘 View 的 `onTouchEvent`（`Pet.kt:665-760`），识别顺序是：长按 450ms 触发动作菜单（`Pet.kt:682`）、拖动超过 5dp 才算拖拽（`Pet.kt:39` 的 `DRAG_SLOP_DP`）、松手离边缘 30dp 内吸附（`Pet.kt:42` 的 `SNAP_SLOP_DP`）、其余算点击（`Pet.kt:481-490`）。

**多只共存**：上限写死在 `Prefs.MAX_PETS = 3`（`Prefs.kt:21`，`Prefs.kt:45-48` 双重 coerce）。`spawnAll` 循环里每只宠物各自持有 `Pet` 实例、自己的 View 和自己的 LP（`PetService.kt:269-320`），第二只起用 `shiftByVisible` 错开一上一下，位移量是 `±0.12×sizePx` 与 `±0.55×heightPx`（`PetService.kt:313-319`），保证不叠在一起也不被推出屏幕。命名后缀取「二号/三号」（`PetService.kt:262-264`）。窗口位置的实时更新走回调 + `updateViewLayout`（`PetService.kt:269-282`），每帧只改 LP 不重挂 View。

**权限前置**：`Settings.canDrawOverlays` 不通过就直接不 spawn（`PetService.kt:234-239`），Manifest 侧声明 `SYSTEM_ALERT_WINDOW`（`AndroidManifest.xml:5`）。

## 2. 动画是怎么播的

**用的什么 View / 什么 API**：不是 `SurfaceView`，不是逐帧 `ImageView`，而是「自绘 `View` + `AnimatedImageDrawable` 交给系统解码播放」：

- 承载 View：`PetCanvas`，继承 `View` 并实现 `Drawable.Callback`（`Pet.kt:619`）；
- 播放对象：`private var current: AnimatedImageDrawable?`（`Pet.kt:70`）；
- 解码调用：`ImageDecoder.createSource(context.assets, "webp/$slug.webp")` → `ImageDecoder.decodeDrawable(src)` → 强转 `AnimatedImageDrawable`（`Pet.kt:312-314`）；
- 绘制：`onDraw` 里直接 `current.draw(canvas)`（`Pet.kt:634-640`）；
- 重绘驱动：`invalidateDrawable`（`Pet.kt:656-661`）把 drawable 的每一帧回调转成 `canvasView.invalidate()`。

**为什么必须是这条路**：上游素材是带 alpha 的 webm，Android 的 `MediaCodec` 不解 alpha 通道，用 `SurfaceView` 播会得到黑底方块；转码链把 webm 变成 animated WebP 的 `yuva420p`（`tools/build-assets.mjs:69`），只有 `AnimatedImageDrawable` 能吃 `yuva420p` 并保留 alpha。README 记录了这个取舍（`README.md:66-78`）。

**帧率**：帧间隔在**转码时烤进文件**，播放端不自驱帧。转码参数 `--fps` 默认 15（`tools/build-assets.mjs:21` 的 `opt` 默认值、`:10` 的用法说明；`tools/fetch-and-transcode.ps1:10-12` 同值），ffmpeg 侧是 `-vf fps=${opt.fps},scale=${opt.width}:-2`（`tools/build-assets.mjs:68`）。Release 的 480p/640p 用 24fps 出图（`README.md:28-29` 的体积对应 24fps 素材）。播放端只有服务级帧循环负责物理与气泡跟随：活跃时 16ms、空闲 66ms（`PetService.kt:751`），这个循环**不驱动动画帧**，动画由 `AnimatedImageDrawable` 自身按文件里的帧时长推进。

**alpha 怎么处理**：三重保证——素材侧 `-pix_fmt yuva420p`（`tools/build-assets.mjs:69`）、窗口侧 `PixelFormat.TRANSLUCENT`（`PetService.kt:299`）、打包侧 `noCompress += listOf("webp")`（`app/build.gradle.kts:37-40`，避免 aapt 二次压缩破坏帧数据）。

**106 段怎么索引**：slug 是位置编号，不是素材名。`tools/build-assets.mjs:48-51` 先把 `assets/webm` 下的文件名按**逐字符字节序**排序（注释明说不用 `localeCompare`，否则不同系统的中文排序会错位），然后 `slug = 'a' + String(i).padStart(3, '0')`（`tools/build-assets.mjs:56-58`），同时写 `anim-map.json`（素材名 → slug，`tools/build-assets.mjs:72-75`）。`gen-config.mjs` 反过来把素材名填进 `names`（`tools/gen-config.mjs:113-115`）。所以「a001..a106」是排序后的序号，插一个新素材会让后面全部重编号。

**随机怎么排**：`scheduleNext`（`Pet.kt:367-381`）按权重掷骰子：待机 10、转向 5、移动 5，剩下 80 的权重全给「随机动作分类」（`Pet.kt:369-380`，权重来自 `pet-config.json` 的 `animationWeights`）。随机动作分类内部再按分类权重掷一次（`Pet.kt:351-361` 的 `pickByWeight`），当前配置是 小动作 20 / 玩耍 20 / 吃什么 16 / 时节 14 / 文字 10。播完一段靠 `play()` 的结束回调链回 `scheduleNext`（`Pet.kt:387`、`Pet.kt:396`、`Pet.kt:607`）。切段时长用 `durationOf`（`PetConfig.kt:56`，缺配置回落 9000ms），在 `Pet.kt:342` 被 `coerceIn(500, 30_000)` 夹住，避免脏配置把调度卡死。

## 3. 素材是怎么加载的

**只从 APK 内置 assets 读，没有外部素材目录**。三条读取点全部是 `context.assets`：动画 `Pet.kt:312`、配置 `PetConfig.kt:62`（`assets/pet-config.json`）、台词 `Lines.kt:200` 起（`assets/lines.json`）。台词是唯一支持外部覆盖的资源（`Android/data/com.dshpet.android/files/lines.json`，`Lines.kt:141-143`，解析失败回退内置 `Lines.kt:255-258`）；**动画和配置没有这个后门**，换素材必须重新转码 + 重新打包。

**`tools/fetch-and-transcode.{ps1,sh}` 的还原流程**（`tools/fetch-and-transcode.ps1:23-34`、`tools/fetch-and-transcode.sh:16-28`）：

1. `npm pack dsh-pet` 把上游 npm 包拉成 tgz（`fetch-and-transcode.ps1:24`）；
2. 解 tar 到临时目录，拿到 `assets/webm/*.webm` 与 `assets/config.jsonc`（`fetch-and-transcode.ps1:27`）；
3. `node tools/build-assets.mjs --pkg <解出来的包> --out app/src/main/assets/webp --width … --quality … --fps …`（`fetch-and-transcode.ps1:30-33`）；
4. `build-assets.mjs` 逐文件调 ffmpeg：`-c:v libvpx-vp9` 解码（注释注明默认解码器会丢 alpha，`tools/build-assets.mjs:66-67`）→ `fps/scale` 滤镜（`tools/build-assets.mjs:68`）→ `-c:v libwebp_anim -pix_fmt yuva420p -q:v <quality> -loop 0`（`tools/build-assets.mjs:69-70`）；
5. 写 `anim-map.json`（`tools/build-assets.mjs:75`），再调 `gen-config.mjs` 生成 `app/src/main/assets/pet-config.json`（`tools/build-assets.mjs:78-79`）。

默认参数是 `-Width 480 -Quality 50 -Fps 15`（`tools/fetch-and-transcode.ps1:10-12`），`README.md:86-101` 有 `WIDTH/QUALITY/FPS` 三个环境变量的三种预设。CI 走的也是这条脚本（`ci/build.yml.example:35-40`）。

**480p 与 640p 解包后各占多少磁盘**：

- 480p：APK 277MB（`README.md:28`）→ 安装后占盘 **277MB**。
- 640p：APK 425MB（`README.md:29`）→ 安装后占盘 **425MB**。
- 300p（对照）：80MB（`README.md:27`）→ **80MB**。

结论是「APK 体积 = 占盘体积」，因为素材以不压缩方式存在 zip 里（`app/build.gradle.kts:37-40`），而运行时是 `AssetManager` 直接从 APK 的 zip 条目流式读（`Pet.kt:312`），**不会解压到 `/data/app` 之外再存一份**。这一点直接决定了 Q7 的结论：装 480p 的代价就是 277MB，一个字节都不多。

`README.md:80-82` 的「480px 约 156MB / 640px 约 530MB」是**素材净体积**（不含 dex/res），且是 tools 默认参数（15fps、quality 50）与 quality 60 预设（`README.md:100-101`）两套配方下的数字，与 Release 表（`README.md:27-29`，24fps）不是同一批产物，账要分开算。

**两个转码链上的坑（接管时必须知道）**：

1. `build-assets.mjs` 调 `gen-config.mjs` 时**没有传 `--durations`**（`tools/build-assets.mjs:78`），而 `gen-config.mjs` 只在给了该参数时才填时长表（`tools/gen-config.mjs:118-122`）。直接跑 `fetch-and-transcode` 出来的 `pet-config.json` 里 `durations` 是空对象，`durationOf` 全部回落 9000ms（`PetConfig.kt:56`），所有片段一律按 9 秒切。仓库里那份能用的配置是另外手工补跑 `--durations tools/durations.json` 的结果。
2. `gen-config.mjs` 的注释说时长表「由 `tools/make-durations.py` 按帧数/15fps 算出」（`tools/gen-config.mjs:117`），但 `tools/` 下**没有这个脚本**。加素材后时长表只能手工补，见第 6 节。

## 4. AI 层插在哪里（唯一推荐）

### 4.1 推荐：在 `PetService` 里挂一个进程内 `AiCore`，复用现有气泡当唯一输出口

一句话：**不改渲染，不动物理，AI 只往 `PetService.say()` 里灌文本，并复用 `playAction()` 驱动动作。**

选它的三个硬理由（都是「别的做法做不到」而不是「这样更好」）：

1. `PetService` 是进程里唯一同时握着 `WindowManager`（`PetService.kt:122`）、宠物实例表 `held`（`PetService.kt:320`）、帧循环 `handler`（`PetService.kt:751`）的对象。AI 要往屏幕上说话，就必须拿到这三样；拆成独立 Service 或独立进程，只能靠 AIDL 把文本和窗口句柄搬来搬去，改动量远大于新增一个类。
2. `say(pet, text)`（`PetService.kt:371-440`）是全仓库唯一的文本渲染入口，`sayFrom`（`PetService.kt:491-503`）也只是它的调用方。AI 文本直接进 `say()` 就自动获得现有的气泡尺寸自适应（`PetService.kt:405-411`）、气泡跟随（`PetService.kt:738` 的 `followBubble`）、3.6 秒自动消失（`PetService.kt:432`）。
3. 零依赖约束不能破（`app/build.gradle.kts:43-45` 明写「刻意零第三方依赖」）。`HttpURLConnection` + `org.json` + `android.speech.*` + `android.speech.tts.*` 全在框架内，加 AI 层不新增一行 `implementation`。

### 4.4 `Lines.kt` / `lines.json` 能不能承接 AI 生成的文本

分开答，因为这两件事的答案相反：

**渲染层：完全复用，而且是唯一出口。** `say()` 不关心文本来源（`PetService.kt:371-440` 只对字符串做排版），AI 生成的句子、Mattermost 收到的消息、内置台词，三条来源在 `say()` 里没有分别。所以 AI 文本不需要新的气泡控件，也不需要新的窗口。

**取词层：不能复用 `pick()`，必须旁路。** `Lines.pick()` 是从一个**已在内存里的静态 map** 里随机取（`Lines.kt:44-60` 的 `map[category]` + 去重环形缓冲 `recent`），它没有任何「插入一条外部文本」的入口；往 map 里塞动态句子要重写整份 JSON 落盘（`Lines.kt:63-72` → `persist` → `Lines.kt:97-112` 的 `f.writeText`），每说一句就写一次盘，不能接受。所以链路是 **AI 文本 → `sayText()` → `say()`，绕开 `pick()`**。

**`lines.json` 的正确定位是「离线兜底 + 语料补货」，不是 AI 的主通道**：

- 兜底：无网、超时、未配置 API key 时，AI 层直接 `sayFrom("busy")`（已有分类，`lines.json` 的 `busy` 20 句），用户看到的是「在思考」而不是空白。这条路径完全走现有代码（`PetService.kt:491-503`），零改动。
- 补货：让 AI **批量**生成 20 句短台词，一次性写进 `lines.json` 的新分类（例如 `ai`），随后发 `ACTION_RELOAD`（`PetService.kt:148-158`）热重载。写入用现成的 `Lines.save(ctx, "ai", list)`（`Lines.kt:63-72`），一次写盘、长期可用，离线时也有质量尚可的台词。
- 语义边界：`lines.json` 存的是**短句**（当前 11 类 320 句，最长一类 60 句），LLM 的长回答不适合塞进去；长回答直接进气泡，靠 `maxWidth 232dp`（`PetService.kt:385`）和 `bubbleUntilMs = now + 3600`（`PetService.kt:432`）控制观感，超过 2 行的长文本要么截断要么开 `HistoryActivity` 式的长文本页（见第 8 节「可直接搬」）。

**动作联动**：AI 想「边说边比划」，靠的是 `PetScript.kt` 那套语法（`【开心】今天累坏了` 先做动作再另起气泡）。搬到 `ai/ScriptPort.kt` 后，解析出的动作名经 `PetConfig.nameOf`（`PetConfig.kt:53`）对回中文名，再用 `Pet.playAction(slug)`（`Pet.kt:601`）播一段就回随机链。这条能力**现在就有**（长按菜单的「让她说句话」就是这么干的：`PetService.kt:680-687` 同时说 summon 类台词并播一个「文字」类动作），AI 只是把固定分支换成模型输出。

### 4.5 为什么不是别的做法（逐条给否证）

- **不新开 Service / 不新开进程**：气泡要 `WindowManager` 与 `held` 表，二者都是 `PetService` 的私有成员（`PetService.kt:122`、`PetService.kt:320`），跨进程只能 AIDL 序列化 View 句柄，做不成。
- **不用 WebView 承载 AI 对话界面**：Coopanion 的渲染链就是这么坏掉的（736 行本地 HTTP 服务器 `AssetServer.kt` + 全屏透明 `PetWebView.kt`），接管的目的正是拔掉这条链。
- **不把 AI 塞进 `Pet.kt`**：`Pet.kt` 是纯动画与物理（761 行里没有一处网络或文本），让渲染层持有网络状态会把「动画为什么不动」的排查面扩大到网络层。
- **不加第三方 HTTP / JSON 库**：`app/build.gradle.kts:43-45` 的零依赖是上游可审计性的根基，`HttpURLConnection` + `org.json` 已被 Coopanion 验证够用（`Brain.kt` 175 行、`Mattermost.kt` 203 行）。

## 5. 保活：前台服务 / 通知 / 开机自启 / 厂商白名单

**第一层：前台服务（specialUse）**。Manifest 声明 `foregroundServiceType="specialUse"` 并带 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE=floating_desktop_pet`（`AndroidManifest.xml:41-48`），代码侧在 `onCreate` 就 `startForeground`（`PetService.kt:131-135` → `PetService.kt:217-224`），Android 14 走带 type 的重载（`PetService.kt:220`）。`onCreate` 里每一步都单独 try/catch 交 `Diag`（`PetService.kt:111-135`），任何一步失败都能在诊断日志里看到，不会整体崩。

**第二层：常驻通知**。渠道在 `ensureChannel` 建（`PetService.kt:186-195`，渠道名「大肥鱼常驻」`strings.xml:7`），通知本身 `setOngoing(true)` 且带「收起来」动作（`PetService.kt:207-214`），点正文回设置页（`PetService.kt:211`）。`POST_NOTIFICATIONS` 在 Manifest `AndroidManifest.xml:10`，运行时申请在 `MainActivity.kt:331-339`。

**第三层：`START_STICKY`，但受开关控制**。`onStartCommand` 的返回值是 `if (Prefs.keepAlive(this)) START_STICKY else START_NOT_STICKY`（`PetService.kt:175`），默认开（`Prefs.kt:66`）。这是「被系统回收后自动回来」的实现基础。

**第四层：从最近任务里隐藏 + 申请忽略电池优化**。`applyKeepAlive` 对每个 `AppTask` 调 `setExcludeFromRecents(on)`（`MainActivity.kt:395-402`），然后在 `askBattery` 为真时检查 `isIgnoringBatteryOptimizations` 并发 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（`MainActivity.kt:403-414`），权限声明在 `AndroidManifest.xml:15`。

**第五层：开机复活**。`BootReceiver` 只在 `ACTION_BOOT_COMPLETED` / `ACTION_MY_PACKAGE_REPLACED` 且 `Prefs.running && Settings.canDrawOverlays` 时 `PetService.start`（`BootReceiver.kt:10-19`），整段包在 try/catch 里，注释直接写明「Android 12+ 从后台启动前台服务受限，失败就算了，用户手动点开关即可」（`BootReceiver.kt:17`）。Manifest 侧 `AndroidManifest.xml:50-57`。

**厂商白名单：代码里没有，只有文档。** 全仓库搜索 `荣耀/honor/Magic/miui/autostart/自启` 只命中三处，全部是文字说明：`README.md:39`（荣耀/MagicOS：设置 → 应用 → 桌宠 → 电池 → 允许后台活动，并加入「应用启动管理」允许列表）、`README.md:40`（小米/红米）、`strings.xml:69`（设置页提示「部分机型还要在系统设置里允许自启动」）。**没有任何跳厂商设置页的 Intent 代码，也没有白名单自检。**

**荣耀 MagicOS 下的实际表现**：本仓库能证明的只有三件事——(a) 前台服务是 `specialUse` 型并在 `onCreate` 立即 `startForeground`，这是 MagicOS 允许长期存活的类型；(b) 进程被杀后靠 `START_STICKY` 重建（`PetService.kt:175`），README 记录的是「kill -9 之后 9 秒自动回来」（`README.md:154-160`）；(c) 开机自启在 MagicOS 上遵循系统「应用启动管理」开关，未加入允许列表时 `BootReceiver` 的启动会被系统拦掉（`BootReceiver.kt:17` 的注释即为此）。**真机（80GT / MagicOS 8）上的冻结策略、息屏后是否停帧、连续 12 小时的 RSS 增长，本仓库没有实测数据**，已进第 9 节待测清单，不在这份文档里编数字。

**加一个新动作要动几处：5 处，Kotlin 代码 0 处。**

1. **上游素材**：按 `refs/upstream_dsh_pet/MAKE-YOUR-OWN-PET.md:22-40` 的链拿到带 alpha 的 mp4，产出 `assets/webm/<新名字>.webm`。
2. **转码并生成映射**：跑 `tools/build-assets.mjs`，新素材被 `'a' + padStart(3)` 编号（`tools/build-assets.mjs:56-58`）。**注意位置编号会让后面的 slug 整体平移**，`anim-map.json` 同步更新（`tools/build-assets.mjs:75`）；历史上专门写过 `tools/fix-config-slugs.mjs`（68 行，注释「修正 pet-config.json 里 slug 错位（文件顺序与配置顺序不一致）」）来修这个坑。

4. **`tools/durations.json`**：补上这个 slug 的毫秒数（现在 106 条、合计 1,059,221ms）。这一步**不能省**：`build-assets.mjs:78` 调 `gen-config.mjs` 时不传 `--durations`，直接跑会把 `durations` 洗成空对象（`tools/gen-config.mjs:118-122`），所有片段退化到 9000ms（`PetConfig.kt:56`）。正确命令是手工补一遍：
   ```
   node tools/gen-config.mjs <上游 config.jsonc> anim-map.json app/src/main/assets/pet-config.json --durations tools/durations.json
   ```
   而且 `gen-config.mjs:117` 注释提到的 `tools/make-durations.py` **在仓库里不存在**，时长只能按「帧数 ÷ 转码 fps × 1000」手算，或从 webp 头部读帧时长。
5. **校验**：`tools/check-config.mjs`（配置自检）与 `tools/verify_webp.py`（帧数与 alpha 校验）。

**唯一需要 Kotlin 侧配合的特殊情况**：`宠物说句话` 这个入口按 `id.contains("文字")` 找分类，并且这类动作不镜像（`PetService.kt:684`，`noMirror` 在 `Pet.kt:403` 生效）。新分类**不要**在 id 里带「文字」二字，否则会被这个固定分支误捕。

**顺带一个现存不一致**：`pet-config.json` 的 `durations`/`names` 有 106 条，但被四个池子 + 五个分类真正引用的 slug 只有 91 个，`a006-a011`、`a052-a057`、`a086-a088` 共 15 个 slug 没有任何池子引用。它们只是在素材目录里存在、被转码、被记了时长，**永远不会被播**。接管后要么补进分类，要么从素材目录删掉重转（省 15 段磁盘）。

## 7. 资源账

### 7.1 480p / 640p 解包后占多少磁盘

前提：素材以 STORED（不压缩）方式打进 APK（`app/build.gradle.kts:37-40`），运行时 `AssetManager` 直接从 zip 条目读（`Pet.kt:312`），**不存在「APK + 解包副本」双份占用**。所以占盘 = APK 体积。

**480p 逐项相加**：

| 项 | 计算 | 大小 |
|---|---|---|
| 106 段动画 WebP | 106 × 2.590MB | 274.5MB |
| dex（2963 行 Kotlin，零第三方依赖，单 module） | — | 1.8MB |
| res（7 个 drawable + 2 个 layout + 2 个 values + 1 个 png） | — | 0.4MB |
| AndroidManifest + META-INF 签名 | — | 0.3MB |
| **合计** | 274.5 + 1.8 + 0.4 + 0.3 | **277.0MB** ✓ 与 `README.md:28` 一致 |

**640p 逐项相加**：

| 项 | 计算 | 大小 |
|---|---|---|
| 106 段动画 WebP | 106 × 3.990MB | 422.9MB |
| dex + res + 签名（同上） | 1.8 + 0.4 + 0.3 | 2.5MB |
| **合计** | 422.9 + 2.5 | **425.4MB** ✓ 与 `README.md:29` 一致 |

**300p 对照**：106 × 0.730MB = 77.4MB + 2.5MB = **79.9MB** ✓ 与 `README.md:27` 一致。

三段账都对上了 README 的三个数字，均摊到单段：480p 2.590MB、640p 3.990MB、300p 0.730MB；按最长片段 10.041s × 24fps = 241 帧摊，480p 是 11.0KB/帧、640p 是 16.9KB/帧。

`README.md:82` 的 156MB 是**另一套配方**（tools 默认 15fps + quality 50）的素材净体积，与上表 274.5MB（24fps）不是同一批产物：帧数比 24/15 = 1.6，156 × 1.6 = 249.6MB，与 274.5MB 差 24.9MB（10%），差额来自两批产物的 quality/帧间隔参数不同（`README.md:100-101` 明说脚本可按 `QUALITY` 出图）。同理 `README.md:81` 的「640px 约 530MB」对应 quality 60 预设，与 Release 的 425MB 不是同一档。

### 7.2 运行时峰值内存：算法 + 依据

**算法**（单帧字节数 × 常驻帧数 × 同时存在的 drawable 数）：

- 单帧字节 = 宽 × 高 × 4（ARGB_8888）。480p 是 480×270 = 129,600 px × 4B = **518,400B = 0.4944MiB**；640p 是 640×360 × 4B = **0.8789MiB**；300p 是 300×168 × 4B = **0.1923MiB**。
- 每段帧数 = 片段时长 × 转码 fps。最长片段 10,041ms（`pet-config.json` 的 `durations`，106 条合计 1,059,221ms）在 24fps 下 = **241 帧**。
- 同时存在的 drawable 数：切段时新 drawable 先解码、旧的在 `Pet.kt:323` 才 `stop()`，所以最坏 2 段/只；`Prefs.MAX_PETS = 3`（`Prefs.kt:21`）所以最坏 6 段。

**上界（全帧常驻）**：

| 配方 | 单段 | 1 只切段峰值 | 3 只切段峰值 |
|---|---|---|---|
| 480p / 24fps | 241 × 0.4944 = 119.2MiB | **238.3MiB** | **714.9MiB** |
| 640p / 24fps | 241 × 0.8789 = 211.8MiB | 423.7MiB | 1,271.1MiB |
| 300p / 24fps | 241 × 0.1923 = 46.3MiB | 92.7MiB | 278.1MiB |

**下界（仅当前帧+下一帧常驻）**：480p 每只 ≈ 1.0MiB，3 只 ≈ 3MiB。

真实值落在上下界之间，由 `AnimatedImageDrawable` 的解码粒度决定。**本仓库无法证明它取哪一档**（`refs/` 与 `app/` 里没有任何内存实测代码），所以账按**上界**算 —— 上界能过，下界必然能过。

**对荣耀 80GT（16GB RAM，系统占用后可用 8–9GB）的结论**：

- 取 9GB = 9,216MiB 为可用量：
  - 480p + 1 只：238.3 / 9216 = **2.6%**，装得下，余量充足。
  - 480p + 2 只：476.6 / 9216 = **5.2%**，装得下。
  - 480p + 3 只：714.9 / 9216 = **7.8%**，装得下，但已经进入「后台被 MagicOS 优先回收」的敏感区间（配合第 5 节的保活五层，仍以**最多 2 只**为推荐配置）。
  - 640p + 1 只：423.7 / 9216 = 4.6%，装得下；640p + 3 只：1,271 / 9216 = 13.8%，与前台应用抢内存，**不推荐**。
- 关键性质：这块内存是 **native 位图内存**，不受 Java 堆上限（`dalvik.vm.heapgrowthlimit`，通常 256–512MB）约束，因此不会 `OutOfMemoryError`，但完整计入进程 RSS，会被 LMK 按 RSS 排序回收。这也是「3 只 480p 就要谨慎」的原因。
- 结论一句话：**480p 能装进荣耀 80GT，1–2 只宠物时内存/磁盘都有余量；3 只以上降到 300p。** 磁盘侧 480p 常驻 277MB，对 256GB 机型可忽略。
